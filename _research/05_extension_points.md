## 1. HTTP (чтение)

| Где | Маршрутов | Что отдают |
|---|---|---|
| `web/routes.py` | 150 | 86 HTML (HTMX-фрагменты и страницы), 56 JSON, 8 plain text |
| `web/sse.py:123` | 1 | `GET /events` |
| `web/shared.py` (отдельное приложение, порт 8788, выключено) | 3 | общий вид и форма идеи |

- **Публичного API нет.** `FastAPI(openapi_url=None)` с комментарием «no client but the page it
  serves» (`web/app.py:90`). Версий нет, схем ответов нет: JSON собирается прямо в маршруте.
- 56 JSON-маршрутов — это приватный XHR-слой верстака (`/workbench/*`, `/cards/*`, `/tools*`).
- **Доска, сессии и задачи отдаются только в HTML.** Ни один JSON-маршрут не отдаёт сессии, задачи
  или доску.
- Ближайшее к машинному интерфейсу — текст:
  - `GET /board.csv` (`routes.py:1135`) — строка на сессию, «nothing inferred»;
  - `/standing`, `/shift`, `/seen`, `/scripts`.
- **Авторизация по месту, а не по субъекту:**
  - bind на 127.0.0.1;
  - `TrustedHostMiddleware` (`app.py:94`);
  - `web/origin.py:92-101` отвергает запросы с кросс-сайтовым `Sec-Fetch-Site`, но **запрос без
    этого заголовка пропускает** (`origin.py:11-14`).

  Значит, любой локальный процесс (curl, скрипт агента) уже может POST-ить во все маршруты, включая
  `/tasks`, `/workbench/run` и `/sessions/{id}/message/send` `[ВЫВОД: чтение]`. Для консоли на
  одного человека это приемлемо, но **нового пишущего входа по HTTP добавлять не стоит**.
- Входящих webhook-ов нет. Единственные входящие записи — идея из общего вида и маячок JS-ошибок
  `POST /seen/errors`.

## 2. SSE (чтение)

- Один поток `GET /events`, генератор на клиента.
- Опрос раз в `registry_poll_seconds` = 2 с.
- События `board`, `blocks`, `ideas`, `blockers`, `heartbeat` (`sse.py:26-47`).
- Полезная нагрузка — **отрендеренный HTML**, отправляется только при изменении.
- Нет id событий, нет `Last-Event-ID`, нет JSON, нет фильтров.

**Стабильность:** нулевая. Любая правка шаблона меняет «схему». sse.py изменили 16 коммитов за
2 недели (git). Внешнему потребителю годится только как сигнал «что-то поменялось».

## 3. MCP (чтение, тесты: 56 + 17 зелёных при общем прогоне)

- `python -m agent_desk.mcp` — самописный stdio JSON-RPC, протокол `2024-11-05` (`mcp/server.py:40`).
- Открывает SQLite **напрямую**, веб для этого не нужен. Исключение — `run`: он только ставит
  прогон, а исполняет его движок внутри консоли.
- **18 инструментов**, 7 пишущих, и все они только добавляют строки:

| Чтение | Запись |
|---|---|
| open_ideas, idea, bench, how_it_went, answer_from, the_page, script, where_i_stopped, what_is_known, answer, what_is_here | keep_idea, close_idea, run, keep_script, leave, know, **ask** |

- Пара `ask`/`answer` — единственная существующая петля, где внешний процесс задаёт вопрос, а
  человек отвечает на доске.
- **Стабильность:** имена и аргументы инструментов объявлены схемой, это самая стабильная
  поверхность проекта. Вывод — проза.
- **Не подключён** ни в одном `.mcp.json` или settings.
- **Дефект R1:** `server.py:131` вызывает `Store.open()`, а тот роняет бегущие блоки консоли.

## 4. Модель данных сессий и задач (чтение)

- `observe/model.py` (pydantic, frozen, `extra="ignore"`):
  - `Session` — pid, procStart, sessionId, cwd, name, kind, version, status, updatedAt,
    statusUpdatedAt;
  - `JobEnd` — state, detail, tokens, worktreeBranch; `terminal = state ∈ {done, failed}`;
  - `TranscriptTail`;
  - `AttentionHint` — **вывод хранит наблюдение, из которого сделан**. Это хорошая основа для
    правила №5.
- Store: `block` (queued|running|answered|failed|cancelled), `task` (010 + 012/014/032), `directive`,
  `run`/`run_step`, `asked`, `shift_step`, `known`.
- **Редакция при чтении из store**: текст хранится как есть и вычищается на выходе
  (`store/redact.py`, `repo.py:1527-1532`).
- Стабильность (git):
  - 77 миграций за 14 дней, из них 9 трогают `task`/`run`;
  - все аддитивные, кроме 046;
  - `routes.py` — 158 коммитов.

## 5. Готово ли это как основа приёма внешних источников (прогонов ai-worker)?

**Нет, но почти всё нужное есть по частям** `[ВЫВОД]`.

| Нужно | Есть? |
|---|---|
| Парсер чужого формата в одном модуле, фикстуры, проверка версии | шаблон есть (`observe/`, ADR 0004), для ai-worker — нет |
| Понятие «внешний прогон», источник, ключ идемпотентности | нет: `run` принадлежит верстаку, id — свежий ULID |
| Запись вердикта проверки (pass/fail/not_run) | нет: `check_card` — карточка верстака, а не запись |
| Честная давность («прочитано N с назад») | шаблон есть в `pull`/`ticket` (`052`, `053`: `seen_at`) |
| Машинное чтение того, что принято | нет: только HTML и проза MCP |
| Показ без кнопок управления | придётся явно запретить |

### Что предлагается для ai-worker, и почему не «ingest endpoint»

Реальная поверхность ai-worker — это **его REST API, GET без авторизации на loopback, и SSE на
прогон** (`aiw:control/api/routers/runs.py:54,79,243@5b59158`). Значит, agent-desk должен **читать
API ai-worker**, как он читает `~/.claude/`, а не принимать от ai-worker данные. Это симметрично
правилу «reading is free» и не добавляет пишущей поверхности в консоль.

Контракт чтения (минимум):

1. `observe/aiworker.py` — чистая функция
   `read_runs(json) -> list[ExternalRun] | notices` над `GET /api/v1/projects/{slug}/runs?status=…`
   и `GET /api/v1/runs/{id}`. Фикстуры записываются с живого ai-worker (`docker compose up`
   локально). Проверка версии по `/api/v1/health` или заголовку.
2. Таблица `ext_run`: `(source, external_id)` UNIQUE, project, ticket, mode, status **как есть**,
   phase, sentinel_verdict, tokens, url, `seen_at`. Значения переписываются на каждом опросе,
   история не нужна: она живёт в ai-worker.
3. Цикл опроса раз в 30–60 с в общем `TaskGroup`. Адрес и имя переменной токена берутся из
   `project_link` (`kind='ai-worker'`), как `token_env` в Jira.
4. Рендер — строка в колонке проекта на доске. Прогон без свежего `seen_at` показывается как
   «нет вестей с HH:MM», а не как running (правило №5). `waiting_for_input` показывается **как
   факт** со ссылкой на тикет.
5. **Никаких кнопок**, кроме ссылок. Отвечают в Jira, управляют из Slack или консоли ai-worker.

**Что уже подходит без изменений:** загрузка `project_link`, хранение токена по имени переменной
(`secrets.py`), SSE-событие `board` (строка ai-worker изменилась → доска обновится), редакция на
выходе.

**Альтернатива на случай, если ai-worker так и не будет развёрнут:** каталог
`<workspace>/<project>/runs/<id>/transcript.jsonl` доступен на диске (`aiw:control/run_files.py:3-5`).
Но это второй парсер внутреннего формата ai-worker, и так делать не стоит.

## 6. Зависимость от формата `~/.claude/` (запуск на CLI 2.1.283)

| Источник | Состояние | Как обнаружится поломка |
|---|---|---|
| `sessions/*.json` → `Session` | работает: 3 сессии, 0 ошибок; новых ключей нет | **сразу**: при смене ключа баннер называет поле, сессия пропадает с доски (`registry.py:~135,182`) |
| Новый `status` (например `waiting`) | показывается как есть | **никак**, только глазами |
| Смысл `procStart` | — | **никак**: доска просто опустеет |
| `projects/*/<id>.jsonl` → `TranscriptTail` | работает: 20 свежих транскриптов, 1256 строк; 8 незнакомых типов строк (`mode`, `attachment`, `cost-state`…) безвредно пропускаются | **никак**: при переименовании `ai-title`, `last-prompt` или блоков `content` поля тихо станут `None` |
| `jobs/*/state.json` → `JobEnd` | разбираются все 445, но есть **`blocked` 203, `stopped` 4, `running` 5**, которых фикстуры не знают; новые ключи `needs`, `block.questions`, `suggestedReply` | **никак**: `stopped`/`blocked` считаются бегущими вечно (`observe/model.py:86-96`, `web/autostart.py:76-78`) и держат место autostart |
| Проверка версии | одна: `RECORDED_CLI_VERSION = "2.1.259"` (`observe/model.py:24`) против версии сессии, только совет | **баннер горит постоянно**, и поэтому на него перестают смотреть |
| Флаги `--bg`/`-w` | — | задача падает с текстом ошибки CLI |

**Итог.** Жёстко проверяется только реестр. Дрейф транскриптов и заданий обнаружится, только когда
кто-то перезапишет фикстуры. Дрейф **уже случился** в заданиях, и никто его не увидел.

### Что уже закрывают нативные `claude --bg` / `claude agents` (2.1.283)

**Покрывают (запуск `--help` и `claude agents --json`):**
- **Список всех сессий**, интерактивных и фоновых, в JSON «for scripting». Проверено: 206 записей,
  поля id, cwd, kind, startedAt, sessionId, name, а также `status` у интерактивных и `state` у
  фоновых. Этот источник лучше, чем разбор `sessions/*.json`.
- Запуск с worktree, `attach`, `logs`, `stop`, `rm`, `respawn`, `--max-budget-usd`.
- Состояние `blocked` с вопросами у фоновых заданий.

**Не покрывают, и это остаётся ценностью agent-desk:**
- группировку по origin-репозиторию через проекты и worktree;
- порядок сортировки с разделением «факт / вывод»;
- инбокс, не тратящий контекст, и его MCP-вход;
- вопросы-блоки через `claude -p` с дневным потолком;
- журнал смены;
- редактированный общий вид.

**Рекомендация.**
- Сделать `claude agents --json` основным источником списка сессий. Контракт у него всё равно не
  гарантирован, но это задокументированная поверхность для скриптов.
- `sessions/*.json` оставить запасным путём.
- Транскрипты читать как сейчас, но с баннером «N строк без понятного типа» при росте доли
  незнакомого.
- Для заданий — фикстуры для `blocked`/`stopped` и уведомление о незнакомом `state`.
