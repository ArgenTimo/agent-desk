## Вердикт одной строкой

**Сейчас agent-desk не годится для ежедневной разработки двух проектов.** Ядро (доска и инбокс)
работает на живом CLI 2.1.283. Мешает не нехватка функций, а то, что инструмент **небезопасно
разрабатывать им же самим**.

- Каждый прогон гейта в любом worktree может запустить настоящего агента и мигрировать живую базу.
- Рабочий экземпляр запущен с `--reload` из той же изменяемой копии репозитория.
- История миграций живой БД уже разошлась с `origin/main`.

До уровня «пользуюсь каждый день» нужно **~25–30 ч по минимальному пути** (уборка, изоляция,
стабильный экземпляр, безопасные миграции, два недостающих сигнала на доске) и **~35–45 ч по полному
списку фаз 0+A+B**. Новые возможности для этого не нужны `[ВЫВОД: 06_backlog.md]`.

## Топ-5 разрывов (по частоте в рабочем дне)

1. **Гейт не герметичен.** Stop-хук запускает `make gate` в конце каждого хода каждой сессии. В
   `origin/main` нет `tests/conftest.py`, поэтому гейт вызывает настоящий `claude`, пишет
   `secrets.json` и мигрирует живую БД `[ФАКТ: запуск; tests/unit/test_laying_out.py:56]`. Отсюда
   7 worktree с именами `beri-v-rabotu*` и живая БД на версии 79 `[ВЫВОД]`.
   Частота: десятки раз в день. Исправление — PR #14 плюс перенаправление `data_dir`, около 3 ч.
2. **Нет разделения на рабочий и dev-экземпляр.**
   - `make run` работает с `--reload` из той же копии, куда `land` мержит ветки (`Makefile:93-96`).
   - Любой `Store.open()` помечает незавершённые блоки чужого процесса как failed
     (`agent_desk/store/repo.py:1169-1175,1211`).
   - Миграции идут автоматически, без бэкапа (`repo.py:1183-1214`).

   Частота: при каждом изменении кода. Исправление: 4–6 ч.
3. **Доска не видит самого частого факта «ждёт человека».**
   - CLI уже пишет `blocked` с `block.questions`, `needs` и `suggestedReply` в файлы заданий. Это
     факт, а не вывод из тишины.
   - agent-desk этого не читает, а `JobEnd.terminal` считает `blocked` и `stopped` работающими
     навсегда (`agent_desk/observe/model.py:86-96`) `[ФАКТ: запуск, 203 blocked]`.
   - Баннер «CLI новее фикстур» горит постоянно (`observe/model.py:24`, 2.1.259 против 2.1.283), и
     на него перестают обращать внимание.

   Частота: каждый взгляд на доску. Исправление: 5–7 ч.
4. **Долг слияния и шум в worktree.**
   - 18 открытых PR, 32 worktree (863 МБ), 4 из них с незакоммиченной работой.
   - Дубликаты PR (#15=#16, #8≈#7) и скрытый конфликт номеров миграций (#15/#16 добавляют второй
     `078`) `[ФАКТ: gh pr list, git merge-tree]`.
   - Доска группирует worktree в экземпляры, и мёртвые worktree превращаются в шум.

   Частота: ежедневно, пока не убрано. Исправление: 6–8 ч по `01_repo_cleanup_plan.md`.
5. **ai-worker не виден вообще.**
   - Его сессии Claude идут внутри контейнеров (`claude -p` в runtime-контейнере проекта) и в
     `~/.claude/sessions` не попадают `[ФАКТ: DuckyFlow adapters/model/claude_code.py:314@5b59158]`.
   - ai-worker не зарегистрирован как проект в БД `[ФАКТ: БД, 0 совпадений]`.

   Частота: каждый раз, когда нужна работа над ai-worker. Исправление (полоса только для чтения):
   6–10 ч, и то лишь если ai-worker реально работает, см. ниже.

## Рекомендуемая роль в паре с ai-worker

План владельца: «agent-desk — пульт человека, исполнение уходит в ai-worker». **Я вижу это иначе и
говорю прямо.**

- **ai-worker пока не исполнитель, на которого можно передать работу.**
  - Код есть только в ветке `staging@5b59158`, а ветка по умолчанию `main` — это спецификация без
    кода.
  - Последний коммит сделан 2026-09-10, 17 дней назад.
  - Сквозной прогон (DUCK-68) и развёртывание не подтверждены
    `[ФАКТ: git log origin/staging; plan/biba-boba/list-2-external.md:16-22@5b59158]`.
- **У ai-worker уже есть свой пульт.**
  - Собственная консоль прогонов с SSE и экран тикетов по времени ожидания.
  - Управление через Slack: proceed, status, hold.
  - Спецификация прямо запрещает вторую поверхность одобрений (`docs/15-web-console.md:80-83@5b59158`).

  Кнопки управления ai-worker в agent-desk были бы третьей поверхностью управления.
- **ai-worker работает от тикетов Jira.** У agent-desk и ai-worker Jira нет: в БД 0 тикетов и ни
  одной ссылки на трекер с токеном `[ФАКТ: БД]`. Разработка самих двух проектов идёт в
  интерактивных сессиях на ноутбуке, и ai-worker к ней не подключается.

**Рекомендация.** agent-desk — **обсерватория и инбокс для интерактивной работы на ноутбуке**. Это
то, чего ai-worker не видит в принципе. К этому добавляется **полоса ai-worker только для чтения**:
список прогонов, фазы, вердикт Sentinel, «ждёт ответа в Jira» как факт, ссылки в консоль ai-worker
и Jira. Никаких кнопок, кроме ссылок.

Запуск агентов из agent-desk (`dispatch`, `autostart`, `explore`/`land`, `kicking`, закрытие
сессий) не «передавать ai-worker», а **заморозить за флагом**:

- для локальной работы его уже закрывает нативный `claude --bg` / `claude agents`;
- для работы по тикетам он принадлежит ai-worker, когда тот заработает;
- живых данных почти нет: `run` 0, `kicking` 0, `landed` 0 `[ФАКТ: БД]`.

Подробно в `02_capabilities_and_scope.md`.

## Вердикт по верстаку

**Заморозить за флагом. Как визуализацию ai-worker не развивать.**

- Технически верстак сделан добротно: 771 тест зелёный (запуск). Словарь закрытый: 5 ролей, 5 типов
  линий.
- На живой базе **ни одного прогона** (`run` = 0) и один шаблон `[ФАКТ: БД]`.
- Рендер — клиентское приложение на ~3,3 тыс. строк `console.js` без исполняемых тестов.
- Отображение прогонов ai-worker на `run`/`run_step` возможно, это около 15–20 ч. Но оно
  дублирует «Run detail» консоли ai-worker, требует режима только для чтения и нового ADR, а данных
  для отображения пока нет.

Для полосы ai-worker достаточно простой HTML-строки на доске.
